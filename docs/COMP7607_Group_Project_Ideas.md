# COMP7607 Group Project Ideas

本文档整理五个与课程内容及 HKUDS 研究方向相关的项目设想。每个选题均从项目目标、研究问题、潜在解决方案、实验计划、评价指标、现有工作关系、资源需求和主要风险等方面进行说明。文档不包含选题推荐或优先级排序。

这些设想的新颖性主要针对课程项目及所列相关工作而言。正式确定选题前，仍需进一步开展系统的文献调研，并据此收窄研究问题。

## 1. MemAudit：基于反事实实验的 Agent 记忆审计与选择性验证

### 1.1 项目目标

本项目旨在研究一种面向长期 Agent 的记忆审计方法：不仅判断某条记忆能否被正确检索，还判断它是否真正影响 Agent 的后续决策，以及这种影响是有益还是有害。

项目的核心目标是识别对决策具有实质影响的“承重记忆”（load-bearing memories），仅对其中来源不足、可能过期或存在冲突的记忆进行额外验证，从而在任务可靠性、验证成本和用户体验之间取得平衡。

### 1.2 问题背景与研究问题

长期记忆可以帮助 Agent 保留用户偏好、历史任务状态和既往经验，但检索到一条记忆并不意味着应该无条件使用它。记忆可能已经过期、脱离原始语境、与其他记忆冲突，或在总结过程中由不确定表述被改写为确定事实。

现有记忆评估通常关注记忆问答准确率、召回率或检索命中率，但这些指标不能直接回答以下问题：

- 如果移除这条记忆，Agent 的最终行动是否会改变？
- 这条记忆对任务结果的影响是正面、负面还是可忽略？
- 哪些记忆值得付出额外成本进行二次查证？
- 能否减少不必要的验证和用户询问，同时降低错误记忆造成的风险？

据此，本项目的主要研究假设是：**基于反事实实验的记忆影响评分，可以识别少量对决策有实质影响的记忆，并使选择性验证比“全部信任”或“全部验证”更具成本效益。**

### 1.3 潜在解决方案

系统可分为记忆检索、反事实审计、选择性验证和记忆更新四个模块。

1. **候选记忆检索**  
   沿用现有关键词、向量或混合检索方法，从长期记忆库中取得与当前任务相关的 top-k 记忆，并保留原始来源、时间、适用范围和不确定性表述。

2. **反事实影响评估**  
   对同一任务分别运行“包含某条记忆”和“移除该记忆”的配对 rollout。根据行动是否改变、任务结果是否变化以及变化幅度，计算记忆影响评分。为控制成本，只审计已检索的少量候选记忆，并复用相同任务输入和运行配置。

3. **影响与来源联合决策**  
   将记忆影响评分与来源可靠性、时间有效性、冲突程度和证据完整性结合。高影响但证据不足的记忆触发第二来源查询、工具核验或用户确认；低影响记忆不触发额外验证。

4. **记忆生命周期更新**  
   保存审计结果。对持续产生负面影响的记忆进行降权、标记过期或限制适用范围；对经独立证据确认的记忆保留其证据链，而不是仅保存一个确定化结论。

### 1.4 实验计划

**实验任务与数据**

构造多会话任务集，每个任务包含历史会话、记忆库、当前请求和可验证的标准结果。可选择三类场景：

- 房间预订或资源预订：人数、时间、无障碍要求及预算约束可自动检查；
- 旅行规划：偏好、费用、日期和行程约束可自动检查；
- 编程或文件操作：最终代码、文件状态或测试结果可自动检查。

记忆条件应覆盖长期有效偏好、已改变偏好、相似但无关的记忆、过期事实、传闻式表述、冲突记忆和受污染记忆。测试任务与用于设计审计规则的任务分开。

**对照方法**

- 不使用长期记忆；
- 检索后全部信任；
- 对所有候选记忆进行验证；
- 仅根据记忆文本置信度或来源标签进行验证；
- 完整的反事实审计与选择性验证方法。

**消融实验**

- 去除反事实影响评分，仅使用来源和时间信息；
- 去除来源与不确定性信息，仅使用反事实影响评分；
- 将逐条移除记忆改为随机移除或按相似度排序；
- 比较不同候选记忆数量和验证预算。

**实验控制**

各方法使用相同基础模型、检索器、解码参数和任务集合。对具有随机性的模型输出进行多种子配对实验，并分别报告验证所需的模型调用、工具调用和 Token 成本。

### 1.5 评价指标

- 端到端任务成功率；
- 由错误记忆导致的错误决策率或危险行动率；
- 正确记忆被不必要验证或错误淘汰的比例；
- 验证调用次数、用户询问次数和平均 Token 成本；
- 平均及尾延迟；
- 不同记忆类型下的收益与失败分布；
- 在未见任务和未见记忆模式上的泛化表现。

### 1.6 与现有工作的关系

[AutoMemory](https://github.com/HKUDS/AutoMemory) 关注如何根据 Agent 的任务和架构自动设计、实现及改进记忆系统；[MGP](https://github.com/HKUDS/MGP) 提供记忆写入、检索、治理、生命周期和审计的统一协议。本项目不替代上述工作，而是研究一种基于反事实结果的记忆评估与验证策略。

[Manufactured Confidence](https://arxiv.org/pdf/2606.29279) 讨论了记忆总结将不确定表述转换为确定事实所产生的风险。本项目可将该现象作为一类测试条件，但研究重点是对记忆的实际决策影响进行测量，并据此分配验证预算，而非仅研究记忆文本的改写方式。

### 1.7 资源需求与预期产出

项目不要求训练模型，主要成本来自配对 rollout 和验证调用。可先使用规则明确的模拟环境和少量开源或商业模型完成实验。

预期产出包括记忆审计模块、多会话测试集、对照实验结果，以及不同验证预算下可靠性与成本的分析。

### 1.8 主要风险与应对

- **反事实实验成本较高**：仅审计 top-k 候选，设置固定验证预算，并研究低成本影响近似方法。
- **单条记忆移除不足以刻画联合作用**：增加记忆组合消融，分析多条记忆共同影响决策的情况。
- **模拟任务与真实使用存在差距**：将规则明确的合成任务与少量人工审查的真实轨迹分开报告，避免过度推广结论。

## 2. SeedGuard：面向 AutoResearch 的自适应重复实验与虚假发现控制

### 2.1 项目目标

本项目旨在改进自动研究 Agent 的实验验证机制，使其不会在单次运行取得较好结果后，就立即将修改视为有效提升。系统将在固定计算预算下，自适应决定哪些候选方法值得增加随机种子和重复实验，以减少将随机波动误认为研究进展的情况。

### 2.2 问题背景与研究问题

AutoResearch 的基本循环包括提出修改、运行实验、读取验证结果以及保留或撤销修改。当每次实验只运行一次时，保留决策同时受到方法效果和随机波动影响。随着尝试次数增加，至少出现一次“幸运结果”的概率也会上升，从而产生选择偏差。

本项目关注以下问题：

- 单次验证结果与多随机种子结果之间可能存在多大差异？
- 固定次数重复实验与自适应重复实验，哪一种更能有效利用计算预算？
- 如何区分候选方法的真实提升、随机波动和选择偏差？
- 在相同 GPU-hour 下，能否获得更多经过重复实验确认的有效改进？

主要研究假设是：**将更多重复实验分配给有希望但结果不确定的候选，比“所有候选只跑一次”或“所有候选固定跑多次”更能提高自动研究的统计可靠性。**

### 2.3 潜在解决方案

1. **受控候选生成**  
   Agent 每次修改一个主要因素，例如模型深度、学习率、批大小或优化器设置，并记录修改假设、代码版本和预期影响。

2. **低成本初筛**  
   每个候选先运行一次或少量短实验，获得初始性能、运行时间和资源消耗。

3. **自适应种子分配**  
   根据当前均值、方差、候选与基线差距及剩余预算，决定继续验证当前候选、转向新候选或停止某一方向。可采用置信区间、UCB 或序贯检验作为决策依据。

4. **实验谱系与选择记录**  
   保存代码版本、参数、随机种子、数据划分、验证分数和保留原因，使后续分析能够区分搜索策略和最终模型效果。

5. **独立最终评估**  
   验证集用于搜索和模型选择，测试集在搜索结束前不参与决策。对最终保留下来的方法进行独立重复评估。

### 2.4 实验计划

**实验平台与任务**

以 NanoGPT/Tiny Shakespeare 为主要实验平台，使用固定数据划分和训练时间预算。候选修改可包括：

- Transformer 层数或宽度；
- 学习率与权重衰减；
- 总批大小与设备批大小；
- 优化器或训练循环中的单项改动。

主要指标为 validation/test bits per byte（BPB），同时记录峰值显存、训练速度和实际 GPU-hour。

**对照方法**

- 每个候选只运行一次的贪心 AutoResearch；
- 每个候选固定运行三次后再比较；
- 使用 UCB 选择下一候选、但不进行自适应重复验证的方法；
- 完整的 SeedGuard 方法。

**实验控制与统计分析**

所有方法使用相同初始代码、数据、候选空间和总 GPU-hour。除比较最终分数外，还应使用不同外层随机种子重复整个搜索过程，以估计搜索结果本身的方差。对“被系统保留的改进”进行额外重复实验，估计其可复现比例。

**消融实验**

- 不使用方差信息，仅根据平均分数分配种子；
- 不使用序贯停止规则；
- 改变初筛实验长度；
- 比较不同验证预算及候选数量。

### 2.5 评价指标

- 虚假保留率：被接受为有效、但后续重复实验无法支持的修改比例；
- 可复现改进数量与比例；
- 最终模型的独立 test BPB；
- 达到给定性能所需 GPU-hour；
- 在固定预算内完成的候选数量和重复实验数量；
- 搜索结果的跨运行方差；
- 最终测试性能与搜索阶段验证性能之间的差距。

### 2.6 与现有工作的关系

[Karpathy Autoresearch](https://github.com/karpathy/autoresearch) 提供了由编码 Agent 修改训练代码并依据验证结果保留或撤销修改的实验范式。[AgentPilot](https://github.com/HKUDS/AgentPilot) 进一步研究如何选择父版本、搜索方向和下一步行动，并通过 UCB 或策略记忆提高改进效率。

本项目将研究重点从“下一步尝试什么”转向“什么时候一个实验结果足以被相信”。自适应重复实验和序贯分析本身是已有统计方法，项目的贡献在于将其集成到 Agent 驱动的自动研究流程中，并系统测量其对虚假发现和计算效率的影响。

### 2.7 资源需求与预期产出

项目需要反复运行小型模型训练，但不需要预训练大规模语言模型。计算需求取决于单次实验时长、候选数量和外层重复次数，可通过缩小模型、数据规模和单次训练预算进行控制。

预期产出包括自动实验控制器、完整实验谱系、不同搜索与验证策略的对照结果，以及可靠性和 GPU-hour 之间的关系分析。

### 2.8 主要风险与应对

- **重复整个搜索过程成本较高**：先在小规模代理任务上验证方法，再对少量关键配置进行完整重复。
- **短实验与长实验结论可能不一致**：将训练时长作为实验因素，检查早期停止是否造成排序反转。
- **序贯方法的统计假设未必完全成立**：明确报告假设与局限，并使用独立重复实验检验实际效果，而不是仅依赖理论保证。

## 3. ReceiptAgent：基于机器可检查后置条件的 Computer Use 验证与恢复

### 3.1 项目目标

本项目旨在提高 GUI 或混合工具 Agent 在长任务中的可靠性。系统为每个关键动作定义机器可检查的预期状态变化，并在动作执行后根据真实环境状态判断任务是否按预期推进，从而支持重试、回滚、重新规划或请求用户介入。

### 3.2 问题背景与研究问题

Computer Use Agent 可以完成点击、输入、菜单选择和跨应用操作，但“动作已经执行”不等于“用户目标已经实现”。例如，点击预订按钮后可能出现错误提示、选错日期、选中相邻行，或根本没有产生确认记录。如果 Agent 仅根据动作调用或自己的文字总结判断成功，错误会在后续步骤中累积。

本项目关注以下问题：

- 能否将自然语言目标转化为每个关键步骤的可验证后置条件？
- 独立环境检查是否比 Agent 自我声明或二次自我询问更可靠？
- 后置条件验证能否提高长任务成功率并降低未察觉失败？
- 验证和恢复机制会增加多少步骤、Token 与延迟？

主要研究假设是：**目标级、环境驱动的后置条件验证，可以更早发现动作与预期结果之间的偏差，并改善长任务的端到端可靠性。**

### 3.3 潜在解决方案

1. **结构化 Action Receipt**  
   为关键动作记录用户目标、动作名称、参数、前置条件、预期后置条件和验证方式。例如，预订动作的合格后置条件不是“按钮被点击”，而是“系统返回与指定房间、日期和人数一致的确认编号”。

2. **分层状态读取**  
   优先使用确定性较强的只读信息源，例如文件内容、应用数据库、API 响应、DOM 或 Accessibility Tree；只有无法获得结构信息时才使用截图和视觉模型。

3. **独立结果验证**  
   将实际状态与后置条件比较。可由规则、模式匹配或结构化字段比较完成；视觉检查作为后备，而不是让执行动作的同一 Agent 仅凭自我陈述确认成功。

4. **失败恢复策略**  
   对可逆操作执行重试、回滚或重新规划；对支付、发送邮件等不可逆或高影响操作，在执行前设置用户确认，而不能依赖事后回滚。

5. **混合接口执行**  
   遵循 API、CLI、页面结构、GUI 的优先顺序。对稳定路径使用确定性重放，对未知或动态页面保留模型驱动的 GUI 操作。

### 3.4 实验计划

**实验环境**

在沙盒中选择两至三类环境，例如模拟房间预订、日历管理和文件批处理，也可使用 OSWorld 的可控子集。避免在真实支付、真实邮件或生产系统上进行试验。

**任务条件**

- 正常长任务；
- 点击坐标偏移或相邻元素误选；
- UI 布局变化；
- 工具返回成功但实际状态未改变；
- 页面中出现与任务无关或恶意的指令；
- 需要跨应用传递信息的多步骤任务。

**对照方法**

- 纯 GUI ReAct，不进行独立结果检查；
- 确定性路径重放或 PhoneCLI 式方法；
- 使用同一 Agent 进行自我检查；
- 完整的后置条件验证与恢复方法。

**消融实验**

- 只验证最终状态，不验证中间步骤；
- 只验证中间步骤，不验证最终用户目标；
- 比较结构信息与纯截图验证；
- 去除恢复策略，仅保留错误检测。

### 3.5 评价指标

- 端到端任务成功率；
- 未察觉失败率：系统声称成功但环境状态不合格的比例；
- 错误检测率与误报率；
- 检测后成功恢复率；
- 不可逆或危险动作的错误执行率；
- 不同任务长度下的成功率变化；
- 额外动作数、模型调用数、Token 成本和延迟。

### 3.6 与现有工作的关系

[PhoneCLI](https://github.com/HKUDS/PhoneCLI) 将稳定手机导航编译为可调用命令，并在需要时回退到 GUI，主要解决导航成本、隐私和执行稳定性问题。[ActGuard](https://arxiv.org/html/2609.14987v1) 关注间接提示注入场景下的执行前动作审计。

本项目主要研究执行后的目标级状态验证与恢复，而不是重新实现路径编译或仅进行执行前安全审计。执行前审计和后置条件验证可以组合，但应在实验中分别报告两者的贡献。

### 3.7 资源需求与预期产出

项目不要求训练模型，主要工作是环境搭建、后置条件表示、状态读取接口和任务标注。可使用现有视觉语言模型或工具调用模型，验证逻辑尽量采用确定性规则。

预期产出包括 Action Receipt 原型、带故障注入的任务环境、验证与恢复模块，以及不同任务长度和故障类型下的实验结果。

### 3.8 主要风险与应对

- **为所有动作编写后置条件工作量过大**：聚焦少量高影响动作和明确环境，研究由工具 schema 自动生成部分条件的方法。
- **视觉验证本身可能出错**：优先使用结构化、只读证据，并对视觉验证单独报告误差。
- **并非所有操作均可回滚**：将可逆与不可逆任务分开，不可逆操作采用执行前审批，不声称可以通用撤销。

## 4. EvidenceLineage：面向多智能体系统的证据相关性建模与验证分配

### 4.1 项目目标

本项目旨在研究一种超越普通多数投票的多智能体验证方法。系统不仅统计多少 Agent 支持某个结论，还分析这些结论是否来自相同模型、相同来源、相同工具结果或相似推理路径，并据此估计独立支持程度和分配额外验证资源。

### 4.2 问题背景与研究问题

多智能体系统可以通过并行搜索、角色分工和互相检查提高覆盖率，但 Agent 数量不等于独立证据数量。如果多个 Agent 使用相同模型、读取相同错误网页或共享同一中间结论，它们可能一致地产出错误答案，多数投票反而会增强错误结论的权重。

本项目关注以下问题：

- 如何表示一个答案所依赖的模型、来源、工具调用和中间结论？
- 能否利用这些信息估计多个答案之间的相关性？
- 证据相关性建模能否降低“共享错误来源导致的一致错误”？
- 与所有结论都验证或仅根据置信度验证相比，能否降低验证成本？

主要研究假设是：**将证据血缘和答案相关性纳入验证决策，可以在相近预算下减少多智能体系统中的相关性错误传播。**

### 4.3 潜在解决方案

1. **证据血缘记录**  
   为每项结论记录负责 Agent、模型与提示版本、引用来源、工具调用、关键中间结果及时间戳，形成可追溯的证据图。

2. **相关性估计**  
   根据模型重合度、来源重合度、工具结果重合度、答案语义相似度和推理路径相似度，估计答案之间的依赖程度。这里的“相关性”是可观测代理指标，不将其直接等同于严格的统计独立性。

3. **独立支持度汇总**  
   对高度相关的答案进行聚类或降权，避免同一来源通过多个 Agent 被重复计票。将来源数量、来源独立性和结论支持关系共同纳入评分。

4. **影响感知的验证分配**  
   优先验证对最终答案影响大、独立支持不足或不同证据链相互冲突的结论。验证可包括新来源检索、不同工具检查、不同模型复核或规则验证。

5. **最终结论生成**  
   输出结论时同时保留支持证据、冲突证据和验证记录，使用户能够区分“多个 Agent 同意”和“多个独立证据支持”。

### 4.4 实验计划

**实验任务**

使用固定语料的多跳研究问答、报告生成或代码验证任务。代码任务可通过测试提供自动结果，研究任务则要求预先标注必要证据和可接受答案。

**受控错误条件**

- 所有 Agent 共享同一错误来源；
- 少数 Agent 获得独立正确来源；
- 不同 Agent 独立产生不同错误；
- 多个答案文本一致但证据链不同；
- 不同证据链支持相互冲突的结论。

**对照方法**

- 单 Agent；
- 多 Agent 普通多数投票；
- Best-of-N 或仅按模型置信度选择；
- 对所有关键结论进行验证；
- 仅根据输出置信度进行选择性验证；
- 完整的证据相关性建模与验证分配方法。

**消融实验**

- 只使用模型身份信息；
- 只使用来源重合度；
- 只使用工具或中间结果血缘；
- 使用完整证据图；
- 改变验证预算和相关性阈值。

### 4.5 评价指标

- 最终答案准确率或任务成功率；
- 共享错误来源条件下的一致性错误接受率；
- 独立正确证据被多数错误覆盖的比例；
- 必要证据覆盖率和引用支持率；
- 验证调用次数、Token 成本和端到端延迟；
- 不同验证预算下的可靠性—成本曲线；
- 若系统输出概率，则额外报告 Brier score 和校准误差。

### 4.6 与现有工作的关系

[AutoSwarm](https://github.com/HKUDS/AutoSwarm) 关注不同 Agent 的统一调用、上下文共享、任务分配和结果综合。[AVA](https://github.com/llmsresearch/AVA) 研究在预算约束下对搜索、采样和验证进行自适应计算分配；[OMVV](https://arxiv.org/html/2610.02632v1) 研究在线环境中对多个验证器进行成本感知选择。

本项目不将“自适应验证”本身作为唯一创新点，而是聚焦多智能体答案之间的**来源和证据依赖关系**。自适应验证器选择可作为对照或组件，证据相关性建模才是主要研究对象。

### 4.7 资源需求与预期产出

项目不要求模型训练，主要成本来自多 Agent 调用、来源采集和验证调用。可先通过固定语料和模拟 Agent 输出控制成本，再在真实多 Agent 轨迹上验证方法。

预期产出包括证据血缘数据格式、相关性估计与验证分配模块、受控错误任务集，以及不同协作和验证策略的对比结果。

### 4.8 主要风险与应对

- **真实独立性难以证明**：将结论表述为基于可观测特征的相关性估计，并使用受控实验提供明确的相关性真值。
- **证据血缘记录增加系统复杂度**：先覆盖模型、来源和工具三类信息，再逐步扩展至中间推理结果。
- **多 Agent 实验成本较高**：使用固定语料、缓存工具结果和限制验证预算，保证各对照组成本可比较。

## 5. SoundReward：面向“答案正确但过程错误”的过程验证奖励

### 5.1 项目目标

本项目旨在研究一种同时评估最终答案和中间推理过程的训练与筛选方法，减少模型因最终答案检查器的盲区而强化错误推理的情况。项目将在可自动验证的数学任务中，对“只奖励最终答案”和“同时验证推理过程”的方法进行公平比较。

### 5.2 问题背景与研究问题

最终答案奖励易于自动计算，但可能将碰巧正确的答案视为完全成功。例如，错误的算术或单位换算仍可能产生目标数值。如果这类回答在 RL 或训练样本筛选中获得满分，模型可能学习到不可泛化的推理模式。

本项目关注以下问题：

- 最终答案正确率与完整推理有效率之间有多大差距？
- 过程验证能否降低“答案对但过程错”的样本进入训练或获得高奖励的比例？
- 在相同数据、模型和训练预算下，过程验证奖励是否提高未见任务上的泛化？
- 更严格的过程检查是否会误伤合法但形式不同的解法？

主要研究假设是：**对可执行推理步骤进行验证，可以减少幸运正确答案造成的奖励噪声，并提高模型的整体推理有效率；其收益需要与检查器覆盖率和训练成本共同评估。**

### 5.3 潜在解决方案

1. **可执行推理表示**  
   将模型解答解析为表达式、步骤或有向计算图，而不是只读取最后一个数值。Countdown 任务可表示为算术表达式树，GSM8K 类任务可表示为带单位的连续计算步骤。

2. **过程检查器**  
   检查数字使用是否符合题目约束、每步算术是否成立、单位换算是否合法、中间结果引用是否一致，以及最终答案是否来自有效推导链。

3. **训练样本筛选**  
   首先使用 rejection sampling：仅保留最终答案和过程均有效的教师解答，用于监督微调，降低直接进行 RL 的工程和计算要求。

4. **过程验证奖励**  
   资源允许时，将奖励拆分为最终正确性、过程有效性和格式可解析性，与最终答案-only 奖励进行对照。应避免仅因模型采用不同但合法的表达形式而惩罚它。

5. **错误类型分析**  
   将失败划分为最终答案错误、单步计算错误、单位错误、无效数字使用、逻辑跳跃和解析失败，分析训练究竟改善了哪类行为。

### 5.4 实验计划

**数据与任务**

- Countdown：可精确检查数字使用次数、运算符和中间计算；
- GSM8K 或单位明确的数学应用题：可检查最终答案、关键计算和单位换算；
- 额外构造“最终答案碰巧正确但过程错误”的对抗样本，用于测量检查器盲区。

**对照方法**

- 基础模型或未额外训练的 SFT 基线；
- 仅按最终答案筛选样本的 SFT；
- 按最终答案和过程共同筛选样本的 SFT；
- 资源允许时，比较最终答案-only GRPO 与过程验证 GRPO。

**实验控制**

各组使用相同基础模型、训练问题、可生成样本数、训练 Token 或优化步数及解码预算。训练题、验证题和最终测试题按题目模板或问题族划分，避免近重复泄漏。

**消融实验**

- 仅检查算术，不检查单位；
- 仅检查最终步骤，不检查完整推导链；
- 比较不同过程奖励权重；
- 比较严格解析与较宽松的合法解法匹配；
- 对检查器误判进行人工抽样审查。

### 5.5 评价指标

- 最终答案准确率；
- 完整推理有效率；
- 幸运正确率：答案正确但过程无效的比例；
- 合法解法被检查器错误拒绝的比例；
- 未见题目模板上的泛化准确率；
- 平均输出长度和 Token 成本；
- 达到目标性能所需训练样本、模型调用和 GPU-hour；
- 各类推理错误的分布变化。

### 5.6 与现有工作的关系

NanoChat 和课程中的 Countdown 示例展示了使用最终答案或规则检查器提供可验证奖励的基本方法。过程奖励和逐步验证也已有相关研究，例如 [Let’s Verify Step by Step](https://arxiv.org/abs/2305.20050)，因此不能将“检查中间过程”本身表述为全新概念。

本项目的具体研究对象是：在小模型、有限训练预算和可执行任务中，如何构建兼顾算术与单位的检查器，并系统测量最终答案奖励的幸运正确问题、过程检查器的误判及其对泛化的影响。

### 5.7 资源需求与预期产出

样本筛选和 SFT 可使用较小开源模型完成；GRPO 阶段的资源需求明显高于纯推理实验，应作为根据实际 GPU 条件决定是否开展的部分，而不是在项目开始时假定一定可用。

预期产出包括过程检查器、带过程有效性标注的数据集、训练与评估代码，以及最终答案和过程有效性的联合分析。

### 5.8 主要风险与应对

- **自然语言推理解析不完整**：优先采用结构化输出和可执行任务，并报告解析失败率。
- **检查器误伤合法解法**：引入等价表达式检查和人工抽样，单独报告 false rejection。
- **过程奖励导致输出模板化**：保留多样化测试题，检查模型是否只学会满足格式而没有提高真实推理能力。
- **RL 计算预算不足**：将过程筛选 SFT 作为完整对照实验，RL 仅在相同预算能够公平比较时加入。

## 共同的实验与报告原则

无论选择哪个方向，实验设计都应遵循以下原则：

- 在实验开始前明确任务成功条件和主要评价指标；
- 将训练、验证和最终测试数据分离，防止近重复样本泄漏；
- 各对照组使用相同模型、任务、工具和解码预算；
- 同时报告质量、Token、工具调用、延迟及计算资源，而不只报告单一准确率；
- 对关键结果进行重复实验或人工抽查，区分随机波动与稳定改进；
- 保留失败案例，并分析系统边界，而不只展示成功演示；
- 对涉及文件、网页、GUI 或外部工具的实验使用沙盒和合成数据，避免对真实服务或用户数据造成影响。
